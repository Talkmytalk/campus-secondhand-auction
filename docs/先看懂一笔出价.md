# 先看懂一笔出价

你暂时不需要理解所有代码。先能说清楚“一笔出价怎样被接受或拒绝”，就能理解自己负责的核心部分。

## 一、拿一个例子看规则

A 发布台灯，起拍价 20 元，最低加价 2 元，今晚 20:00 截止。

- 没人出价时，B 出 20 元，可以接受。
- 当前最高价为 20 元时，C 出 21 元，不够最低加价，拒绝。
- C 出 22 元，可以接受；出 23 元也可以接受。
- A 是卖家，不允许给自己的台灯出价。
- 到晚上 20:00，即使页面还没刷新，也不能再出价。
- 截止时如果 C 的 23 元最高，C 获胜，系统生成 23 元的待模拟付款订单。
- 只有 C 能点击该订单的模拟付款；点击后只更新记录，不扣钱。

## 二、页面、接口、业务和数据库各做什么

页面负责让用户输入价格、点击按钮和看到结果。后端不能相信页面已经检查过价格，因为请求可以被修改。

接口是页面与后端约定的入口。例如 `POST /api/auctions/1/bids` 的意思是“给编号为 1 的拍卖提交出价”。请求只需要带金额，身份通过登录令牌判断。

业务处理负责决定这次出价是否有效。它读取这场拍卖，检查卖家、截止时间和最新价格，再决定保存还是拒绝。

数据库负责长期保存账号、拍卖、出价记录、订单和登录会话。后端重启后，仍然能读取已经提交的记录。

## 三、按这个顺序读代码

1. `web/AuctionController.java` 中的 `bid`：接收请求，从令牌取得当前用户。
2. `service/AuctionService.java` 中的 `placeBid`：锁定并读取拍卖记录，再交给校验器判断。
3. `domain/BidRules.java` 中的 `validate`：检查是否登录、是否卖家、是否到期、价格是否足够。
4. 回到 `placeBid`：保存出价记录，同时更新最高价和最高出价者。
5. `web/ApiErrorHandler.java`：把拒绝原因转成前端能显示的错误消息。

这些文件都在 `backend/src/main/java/edu/campus/auction` 下。

## 四、为什么需要锁和事务

假设 B、C 同时看到当前没有出价，都提交 20 元。如果都只检查各自之前读到的旧数据，就可能都显示出价成功。

代码使用数据库行锁：同一时刻，一场拍卖的关键更新只让一个请求处理。第二个请求等第一个完成后，再读取最新价格。此时它需要至少出 22 元，所以原来的 20 元会被拒绝。

事务保证“保存出价记录”和“更新最高价”一起成功；其中一步失败时，一起撤销，避免留下不一致的数据。到期结算也使用同一场拍卖的行锁。

独立的 `BidRules` 校验器本身不提供并发控制；必须把它放在取得锁之后、同一事务中使用。

## 五、拍卖状态与订单状态不同

拍卖有三种状态：进行中 `RUNNING`、已成交 `SOLD`、流拍 `UNSOLD`。

成功结束的拍卖会有一笔订单。订单先为待模拟付款 `PENDING_PAYMENT`，买家操作后变为已模拟付款 `PAID`。因此，拍卖已成交不等于已经付款。

## 六、向老师介绍时可以覆盖这些点

- 系统的核心流程和第一版功能范围。
- 后端如何校验身份、价格和截止时间。
- 多人同时出价时，为什么不会都依据旧价格成功。
- 为什么一场拍卖只能有一笔订单，以及重复付款如何处理。
- 哪些测试已实际通过，哪些页面联调和人工测试还没完成。

先亲自运行和试用，再用自己的话描述；不需要背下所有类名。
