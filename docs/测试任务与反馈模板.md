# 测试任务与反馈模板

交接日期：2026 年 10 月 23 日。本文件用于测试成员独立执行测试；已有的《测试记录》属于此前后端自动验证证据。

## 一、先做什么

1. 按交接说明启动后端，确认健康检查返回 UP。
2. 阅读《接口说明》和《业务规则初稿》，理解成功、拒绝和权限要求。
3. 使用熟悉的 HTTP 接口测试方式，注册卖家 A、买家 B、竞拍者 C 三个账号并登录，分别保存实际令牌。
4. 先执行《测试用例清单》中正常流程、价格规则、截止时间、订单权限和模拟付款用例。
5. 页面完成后，再补页面交互、页面错误提示、时间显示及完整流程验证。

测试可以从接口立即开始。第一版未接真实支付，不发生实际扣款。

## 二、第一批优先检查

| 重点 | 对应场景 |
| --- | --- |
| 基本流程 | 注册 → 登录 → 发布 → 出价 → 到期 → 查询订单 → 模拟付款 |
| 身份校验 | 未登录不能发布或出价；卖家不能给自己出价；非买家不能付款 |
| 价格规则 | 首次可等于起拍价；以后必须满足最低加价；零、负数和超精度金额被拒绝 |
| 结束规则 | 截止后不能出价；有有效出价才产生订单；无人出价流拍 |
| 付款规则 | 金额由后端决定；重复付款保持同一订单和原付款时间 |
| 数据保留 | 停止后重启同一目录下的后端，核对已提交的数据 |

建议先使用起拍价 20 元、最低加价 2 元、几分钟后截止的拍卖。每条用例记录自己的前置数据；需要“无人出价”的场景时新建一场拍卖，避免与前面的出价记录混淆。

令牌到期、同时请求等用例如果暂时不能执行，标记“待执行”并说明原因。并发场景需要同时发送请求，不能仅凭先后点击两次判断通过。不要为了测试令牌到期而修改整台电脑的系统时间。

## 三、测试记录如何填写

使用包内《测试执行记录_待填写》逐条记录。初始状态均为“待执行”，可修改为“通过、失败、阻塞”。

记录执行日期、测试环境、实际操作与结果，并附响应内容或截图位置。用例失败时，给出问题编号，方便修复后复测。同一问题修复后应保留首次发现记录，再补复测结果。

## 四、问题反馈模板

每个问题复制以下模板填写：

```text
问题编号：例如 BUG-001
测试人／日期：
环境：操作系统、Java 版本、后端版本、是否已接页面
问题标题：
前置条件：使用哪个角色、拍卖是否有出价、是否已到期
复现步骤：
1.
2.
接口方法与地址：
请求参数：隐藏密码和令牌，保留与问题有关的字段
预期结果：
实际结果：HTTP 状态、响应内容或页面现象
截图／记录位置：
影响：是否导致主要流程无法继续
复测结果／日期：待修复后填写
```

## 五、测试同学应交回的成果

- 已执行用例、通过／失败／阻塞／待执行数量，以及测试环境。
- 填写后的执行记录与必要的截图或接口响应。
- 问题清单和修复后的复测记录。
- 哪些流程已验证、哪些尚未验证的简短结论。
